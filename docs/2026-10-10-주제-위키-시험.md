# 주제 뽑기를 LLM 위키로 — 시험 리포트 (2026-10-10)

결론: **주제는 위키(주제 지도)로 쌓는다.** 멘토가 세 방식의 최종 주제 후보를 블라인드로 보고 "위키 방식이 훨씬 낫네. 이걸로 가자"(2026-10-10)로 정했다.

## 1. 문제

- 지금 방식(`scripts/topic_candidates.py`)은 서재의 원문 전부(경영일기 제외)를 astra에게 한 번에 주고 주제 후보를 받는다. 지난 회차도, 이미 쓴 글도 모른다.
- 같은 원문 22편으로 세 번 뽑았더니 "내 전문성의 활동 반경"이 세 번 다 나오고 인수인계·왜 더 바쁜가·요약과 분석·분석을 멈출 때가 되풀이됐다.
- 원문이 늘면 한 번에 읽는 양이 계속 커진다. 40편에서 프롬프트가 명령줄 인자 한도(128KB)를 넘어 주제 뽑기가 멈췄다(표준입력으로 고쳐 해결). 수백 편이면 주목도가 흐려지고 결국 읽을 수 있는 양을 넘는다.

## 2. 검토한 길

| 길 | 판단 |
|---|---|
| Supabase 벡터 DB | 버림. 원문 대부분이 "AI·자동화"라 벡터상 다 가깝게 붙어 묶음이 쓸모없고, 인프라만 는다 |
| Karpathy LLM Wiki 패턴 | 채택. 원문(불변) · 위키(LLM이 쓰고 고침) · 규칙 파일 세 층, 넣기(ingest)·묻기(query)·점검(lint) |
| OKF v0.1 (Google) | 형식으로 채택. YAML 머리말 `type` 필수, 예약 파일 `index.md`·`log.md`, 표준 Markdown 링크 |
| Hermes Agent | 안 씀. 이 PC에 없고, 위키만을 위해 실행 환경·기억을 하나 더 둘 이유가 약하다. llm-wiki 스킬의 규칙만 참고 |
| 오픈소스 8개 (aside 조사, `runs/studio/llm-wiki-oss-조사-20261010.md`) | [Astro-Han/karpathy-llm-wiki](https://github.com/Astro-Han/karpathy-llm-wiki)(MIT)를 바탕으로. "같은 핵심 논지면 기존 페이지에 합친다"가 되풀이 문제를 정면으로 다룬다. llm-wiki-compiler는 임베딩이 필요하고 중복 판정이 제목 일치 수준이라 뺐다 |

우리 쪽 보강: 페이지 단위를 "칼럼 한 편이 될 하나의 논지"로, 원문 목록(경로·URL·작성자·날짜·보태는 것) 필수, 쓴 글 표시, 원문 문장 옮기지 않기, 위키는 목차일 뿐 글은 원문 전체로. 원문 보호는 지침이 아니라 실행 환경으로 강제했다 — astra를 `wiki/` 안에서만 쓰기 가능한 샌드박스(`codex exec -s workspace-write -C wiki`)로 돌려, 원문 폴더에 쓰면 "읽기 전용 파일 시스템"으로 막힌다(시험으로 확인). 규칙은 `wiki/AGENTS.md`.

## 3. 시험 설계

같은 원문, 같은 순서(10-07에 모은 22편 → 10-10 자동 수집 18편)로 세 방식을 돌려 원문 40편 시점의 최종 후보를 비교했다. 별도 워크트리(`wt/wiki`)에서 하고, 쓰던 작업실은 건드리지 않았다.

- **A 지금 방식** — 기존 회차 그대로(22편으로 3회, 40편으로 1회).
- **B 지금 방식 + 기억** — 같은 지시에 "이미 낸 주제·이미 쓴 글과 겹치지 않게"만 더함(22편 2회차, 40편 3회차). 앞서 제안했던 값싼 땜질.
- **C 위키** — 22편을 한 편씩 넣기 → 정리 → 18편 넣기 → 후보 내기.

미리 정한 판단 규칙: **B가 C만큼 좋으면 B.** 주제의 질은 LLM 채점 없이 멘토가 1·2·3 블라인드로 판단하고, 기계 지표는 보조 근거로만 쓴다.

## 4. 결과

| | A 지금 | B 지금 + 기억 | C 위키 |
|---|---|---|---|
| 최종 후보 수 | 15 | 11 | 20 (주제 페이지 22 중 쓴 글 2개 제외) |
| 앞 회차와 겹치는 주제 | 10 | 0 | 10 — 단 회차마다 새 카드가 아니라 한 페이지에 쌓임 |
| 작성자 2명 이상인 주제 | 15 | 2 | 11 |
| 원문 1편짜리 주제 | 0 | 8 | 9 |
| 후보에 쓰인 원문 (40편 중) | 30 | 15 | 35 |
| 새 18편 중 후보에 쓰인 것 | 12 | 14 | 14 |
| 새 18편 처리 | — | — | 합침 9 · 새 주제 7 · 보탬 없음 2 |
| 걸린 시간 (astra) | 101초 | 116 + 175초 | 처음 40편 약 37분 (22편 20분 · 정리 2분 · 18편 14분 · 후보 1분) |

읽은 것:
- **A**는 되풀이가 그대로다. 회차마다 같은 주제를 새 카드로 다시 쌓고 쓴 글을 잊는다.
- **B**는 되풀이를 없앴지만 얇아졌다. 굵은 주제를 피하느라 원문 하나짜리 곁가지("추천 글의 할인코드", "고객 명단을 절반 지운 이유")로 밀려나 40편 중 15편만 썼다. 회차를 거듭할수록 더 얇아질 방식이다.
- **C**는 예전 주제가 다시 나오되 논지 하나에 카드 하나로 남고, 새 원문 절반이 기존 주제에 합쳐져 두꺼워졌다("AI가 다시 찾을 업무 기록을 남기자" 원문 5편, "AI에게 목적과 조건부터" 5편). 쓴 글 두 개(퇴근 시간 칼럼 · 작은 반복부터)는 위키가 알아서 표시해 후보에서 뺐다.
- 남은 약점: C의 원문 1편짜리 주제 9개 — 재료를 더 모으거나 정리에서 묶을 대상. 위키 이력에 넣기 줄이 45개(원문 40편, 5편은 두 번 적힘).

멘토 판단(블라인드 후 공개): **위키 방식이 훨씬 낫다.**

## 5. 작업 방식이 어떻게 바뀌나

| | 전 | 후 (위키) |
|---|---|---|
| 멘토가 하는 일 | 수집 → 주제 뽑기 → 회차별 목록에서 고르기 | 수집만 하면 새 원문이 위키에 들어감 → 주제 지도에서 고르기 · 가끔 정리 결과 확인 |
| AI가 도는 때 | 주제 뽑기를 누를 때마다 원문 전체를 처음부터 | 수집이 끝날 때 새 원문만(1편에 1분 안팎) · 고를 때 그 주제 원문만 깊게 |
| 주제 화면 | 회차별 카드 목록(되풀이가 쌓임) | 분야별 주제 지도 — 카드마다 원문 수·새 재료·쓴 글 |
| 서재가 커지면 | 한 번에 읽는 양이 계속 는다 | 한 번에 읽는 양은 새 원문 + 관련 주제 페이지뿐 |
| 사람이 쥐는 것 | 카드 고르기 | 카드 고르기 + 정리(합치기) 확인. 위키가 바뀐 내용은 git 기록으로 보인다 |
| 그대로인 것 | 제목 후보(astra) · 과정 1·2·3 · 피드백 · 분량 · 그림 · 확정. 글은 언제나 원문 전체로 | |

## 6. 시험하지 못한 것

- 원문 40편, 넣는 순서 한 가지로만 시험했다. 수백 편 규모는 아직이다(Karpathy 원문이 상정한 규모는 원문 약 100개, 그 뒤로는 검색 도구 qmd를 붙이라고 한다 — 필요해지면 그때).
- 고를 때 그 주제 원문만 깊게 읽는 단계, 수집 뒤 자동 넣기, 주제 지도 화면은 이 시험 뒤에 만든다.
