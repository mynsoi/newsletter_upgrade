문제

지금 방식은 서재의 원문 전부를 astra에게 한 번에 주고 주제 후보를 받는다. 지난 회차도, 이미 쓴 글도 모른다.

↻같은 원문 22편으로 세 번 뽑으니 "내 전문성의 활동 반경"이 세 번 다 나오고, 인수인계·왜 더 바쁜가·요약과 분석·분석을 멈출 때가 되풀이됐다.
⇡원문이 늘면 한 번에 읽는 양이 계속 커진다. 40편에서 프롬프트가 명령줄 한도(128KB)를 넘어 주제 뽑기가 멈췄다(표준입력으로 고침). 수백 편이면 흐려지고 결국 다 읽지 못한다.

검토한 길

길판단
Supabase 벡터 DB버림 — 원문 대부분이 "AI·자동화"라 벡터상 다 가깝게 붙어 묶음이 쓸모없고, 인프라만 는다
Karpathy LLM Wiki채택 원문(불변) · 위키(LLM이 쓰고 고침) · 규칙 파일, 넣기·묻기·점검
OKF v0.1 (Google)형식으로 채택 — YAML 머리말 type 필수, 예약 파일 index.md·log.md, 표준 Markdown 링크
Hermes Agent안 씀 — 이 PC에 없고, 위키만을 위해 실행 환경·기억을 하나 더 둘 이유가 약하다. llm-wiki 스킬의 규칙만 참고
오픈소스 8개 (aside 조사)Astro-Han/karpathy-llm-wiki(MIT)를 바탕으로 — "같은 핵심 논지면 기존 페이지에 합친다"가 되풀이를 정면으로 다룬다. llm-wiki-compiler는 임베딩이 필요하고 중복 판정이 제목 일치 수준

원문 보호는 지침이 아니라 실행 환경으로 강제했다 — astra를 wiki/ 안에서만 쓰기 가능한 샌드박스로 돌려, 원문 폴더에 쓰면 "읽기 전용 파일 시스템"으로 막힌다(시험으로 확인).

시험

같은 원문, 같은 순서(10-07에 모은 22편 → 10-10 자동 수집 18편)로 세 방식을 돌려 원문 40편 시점의 최종 후보를 비교했다. 별도 워크트리에서 하고 쓰던 작업실은 건드리지 않았다. 미리 정한 규칙: B가 C만큼 좋으면 B. 주제의 질은 멘토가 블라인드로 판단하고, 기계 지표는 보조 근거로만 쓴다.
