# AI 시대 일하는 방식 인사이트 콘텐츠 파이프라인 기획서

> **한 줄 정의**: 외부의 AI·조직문화 콘텐츠를 자동 수집·구조화하고, SK 내부 자료(SKMS·경영층 메시지)와 결합해 **다중 출처 교차 기반의 인사이트 아티클을 주 1편** 발행하는 반자동 파이프라인.
>
> **구현·운영 방식**: Claude Code가 개발과 실행을 담당하고, 사람은 방향 선택과 최종 승인만 담당한다.

|---|---|
| 문서 버전 | v1.1 — 소스 카탈로그 확정 프로세스·변경 거버넌스 추가(4.1~4.2), Phase 1을 α(소스)∥β(인프라) 병행 → 관문(첫 수집) 구조로 재편(12장, phase1-plan 연동) |

**이 문서의 구성**: 3~8장이 시스템의 작동 원리를 설명하는 본체다. 특히 8장은 Phase 0에서 실제로 발행된 아티클 1편이 시스템을 통과한 과정을 **실물 데이터 그대로** 따라간다 — 시스템이 어떻게 돌아가는지는 이 8장 하나로 파악된다. 구현 코드 수준의 세부는 저장소 안에 있으며(부록 C), 운영에 필요하지 않다.

## 1. 왜 만드는가

- AI와 일하는 방식에 관한 콘텐츠는 넘쳐나지만 대부분 "번역된 트렌드 요약"이라 실무 의사결정에 쓰이지 않는다.
- 담당자가 수동으로 자료를 찾고 정리하는 방식은 품질이 담당자의 그 주 상태에 좌우되고 지속 불가능하다.
- 좋은 자료도 SK의 언어(SKMS, 경영층 메시지)로 번역되지 않으면 조직 안에서 힘을 받지 못한다.

**성공의 정의** — 아래를 못 지키면 실패로 간주:

| 구분 | 기준 |
|---|---|
| 필수 | 모든 아티클이 **독립 출처 3곳 이상**을 교차 인용, 그중 1곳 이상은 반대 관점 |
| 필수 | 모든 아티클에 SKMS·경영층 메시지의 구체 문구를 근거로 한 "SK 맥락" 섹션 존재 |
| 필수 | 사실 오류(출처에 없는 수치·인용) **0건** |
| 필수 | 사람 편집 시간 편당 60분 이내 |
| 지향 | "이건 그냥 요약이네"라는 반응이 3개월 내 소멸 |

## 2. 확정된 전제 (의사결정 완료)

1. **운영 인력**: 개발 초기 리더 1 + 실무 1. 운영 단계(Phase 4~)는 2명 주 단위 교대, 사람 개입 **주당 총 90분 이내** 목표.
2. **발행 주기**: 주 1편, 요일 고정.
3. **독자**: 사내 전 구성원 → 용어 풀이, 리더용/실무자용 액션 분리, 푸시 채널 필수.
4. **내부 데이터 (2026-08-26 변경 확정)**: **공개 가능(A등급) 자료만 운용한다.** internal/ 폴더의 규칙은 하나 — "여기 올라간 텍스트는 아티클 생성 시 외부 AI 서버로 전송된다. 전송돼도 되는 내용만 올린다." 판단은 담당자가 하며 별도 승인 절차 없음. 사내한(B등급) 원문은 올리지 않되, 그 가치는 사람이 공개 가능한 요지로 추상화해 A등급 문서로 등록하는 방식으로 활용(7장). 기밀(C)은 어떤 형태로도 투입 금지. → 이 결정으로 **보안 검토는 불필요해졌고 외부 병목이 사라졌다.** 향후 B등급 원문 사용이 꼭 필요해지면 그때 보안 검토 절차를 부활시킨다.
5. **경영층 메시지**: 실명·직책 표기 허용, 발행 전 사람이 건별 확인.
6. **유료 구독**: 예산 확보. 페이월 우회 없이 정식 구독으로 수집.

## 3. 시스템의 뼈대 — 무엇이 어디에 저장되고, 단계 사이를 무엇이 오가는가

### 3.1 여섯 단계와 각 단계의 입출력

이 시스템은 여섯 단계가 이어진 하나의 흐름이다. 각 단계는 **앞 단계의 산출물을 입력으로 받아, 변형하고, 다음 단계에 파일 또는 데이터로 넘긴다.** 단계 사이에 사람의 전달·설명이 필요 없는 이유가 이것이다 — 산출물 자체가 다음 단계의 작업지시서다.

| 단계 | 입력 | 처리 | 출력 | 실행 주기 | 외부 AI(API) 사용 |
|---|---|---|---|---|---|
| ① 수집 | RSS 주소 목록 (sources.yaml) | 새 글 판별 → 본문 추출 → 중복 제거 | 문서 레코드(원문 포함, DB) | **GitHub Actions가 매일 06:00 클라우드에서 자동 실행** (PC 무관) | 없음 (일반 프로그램) |
| ② 정제·분해 | 수집된 원문 | 주제 관련성 판별 → claim 추출 → 태깅 | claim 레코드(DB) | 수집 직후 자동 | **경량 모델** — 외부 공개 콘텐츠만 전송 |
| ③ 토픽 발굴 | 최근 2주 claim 전체 | 유사 claim 군집화 → 신호 점수 계산 | 토픽 후보 5건 (파일) | 매주 월요일 자동 | 의미 유사도 계산만, 점수 계산은 로컬 |
| ④ 증거 수집 | 선택된 토픽 1건 | 관련 claim 검색 + 최소 조건 검사 | 증거 묶음 (JSON 파일) | 사람 선택 후 자동 | 없음 (저장된 claim 검색) |
| ⑤ 앵글→초안→검증 | 증거 묶음 | 논지 후보 3개 → 초안 → 자동 검증 | 초안 + 검증 리포트 (파일) | 사람 앵글 선택 후 자동 | **상위 모델** (내부 자료는 A등급만 — 7장) · 수치 대조·40%·금지어 검사는 API 없이 코드 |
| ⑥ 승인·발행 | 검증 통과 초안 | 사람 체크리스트 검토 | 발행본 | 사람 | 없음 |

**모델 이원화 원리**: API 호출량의 대부분은 ②(매일, 문서 단위)이고 작성(⑤)은 주 1회다. 그래서 대량·단순 작업은 경량 모델, 소량·고난도 작업은 상위 모델을 쓰며, 어떤 모델을 쓸지는 설정 파일 한 곳(config/settings.yaml)에서 관리한다. **보안 연결**: 내부 자료는 ②를 거치지 않는다(색인은 API 없이 로컬 처리). 내부 자료가 API에 실리는 유일한 지점은 ⑤이며, 그때도 "API 전송 가능" 표식이 켜진 자료만 통과한다(7장). ⑤의 검증이 반반인 것도 의도다 — AI의 자기 검증은 관대해지기 쉬우므로, 수치 대조처럼 속일 수 없어야 하는 검사는 결정적인 코드가 수행한다.

### 3.2 저장 구조 — 네 개의 테이블

데이터베이스(외부 관리형 PostgreSQL, Supabase — 11장. 웹 대시보드에서 테이블을 눈으로 확인 가능)에는 성격이 다른 네 개의 테이블(표 형태의 데이터 묶음 — 엑셀 시트와 같은 구조)이 분리 보관된다. 각각의 실물 예시와 함께 보면:

**테이블 1. 문서(documents)** — 수집된 글 1편당 1건. 원문 전문도 body 컬럼에 함께 저장한다(두 PC와 Actions가 같은 원문을 보게 하는 구조).
```
제목: The Hidden Realities of AI Adoption   출처: hbr (T3)
발행일: 2026-08-11   원문: body 컬럼(전문 저장)
본문 지문(해시): a91f…   상태: enriched(claim 추출 완료)
```

**테이블 2. claim** — 문서에서 추출한 검증 가능한 주장 1개당 1건. **이 테이블이 시스템의 심장이다** (원리는 3.3).
```
claim: "근로자들이 생산성 향상을 보고했음에도 기업의 실제 수익에는
       약속된 이점이 나타나지 않았다"
출처 문서: (테이블 1의 HBR 문서를 가리킴)   근거 유형: data
주장 방향(stance): cautious(신중)   수치 근거: 없음
```

**테이블 3. 내부 자료(internal)** — SKMS·경영층 메시지. 외부와 물리적으로 분리된 테이블이다. A등급(공개 가능) 자료만 운용하며, 각 파일의 security 표기와 C등급 자동 거부는 안전벨트로 유지한다(7장).

**테이블 4. 아티클(articles)** — 주의: 글 본문은 여기 없다(본문은 파일로 존재). 이 테이블에 저장되는 것은 두 가지다. ① **관리 대장**: 아티클별 상태(초안→검토→승인→발행/반려+사유), 선택된 앵글, 채점 점수. ② **문단-claim 연결 원장**: "어느 문단이 어떤 claim을 어떤 역할(지지/반대/배경)로 썼다"의 기록 — 논문의 각주·참고문헌을 검색 가능한 데이터로 만든 것이다.
```
예) 문단 "관찰된 신호 ¶2" → claim "개인은 생산성 체감, 조직 수익 미실현"(HBR) → 역할: 지지
    문단 "통념과의 충돌 ¶2" → claim "책무성 없는 안전감은 안주"(이론 카드)   → 역할: 지지
```
이 원장이 있어야 돌아가는 기능이 넷이다: 검증 게이트의 "실사용 근거 기준" 재계산(8장 ⑤-3) · 발행 후 "이 주장 근거가 뭐냐"의 역추적(문단→claim→원문→출처 링크) · 과거 글과의 논지 중복 검사(R-08)와 토픽 미개척도 계산 · "6개월 무인용 소스 제거"의 인용 횟수 집계(4.2). 테이블 1~3이 글의 재료라면 테이블 4는 완성된 글의 족보다.

### 3.3 핵심 원리 — 왜 문서가 아니라 claim 단위로 저장하는가

문서를 통째로 보관하고 "관련 문서를 찾아줘"라고 하면, 시스템은 가장 비슷한 문서 1~2개를 찾아 그 내용을 정리한다 — **구조적으로 요약이 될 수밖에 없다.** 반면 claim 단위로 쪼개 놓으면 서로 다른 문서의 주장들이 같은 테이블 안에서 비교·충돌·결합된다. Phase 0의 실제 사례:

```
claim A (HBR, cautious):  개인은 생산성 향상을 체감하는데 기업 수익에는 안 나타난다
claim B (HBR, optimistic): 생성형 AI의 수익은 개인 도구가 아니라 조직 전체 솔루션에서 난다
claim C (이론 카드, conditional): 심리적 안전감이 높아도 성과 기준·책무성이
                                 함께 높지 않으면 학습·성과로 이어지지 않는다
```
A와 B는 서로 모순처럼 보인다. 그런데 C를 렌즈로 대면 하나의 구조가 보인다 — "실험의 자유(안전감)만 열고 확인 기준(책무성)을 설계하지 않으면, 개인 체감이 조직 성과로 연결되지 않는다." **이 명제는 세 출처 어디에도 없다. 세 claim의 교차점에서만 나온다.** 이것이 이 시스템이 정의하는 인사이트이고, claim 단위 저장은 이 교차를 가능하게 하는 유일한 구조다.

### 3.4 설계 원칙 4가지

1. **모든 중간 산출물은 파일로 남긴다** — 토픽 후보·증거 묶음·앵글·초안·검증 리포트 전부. "왜 이런 글이 나왔나"를 언제든 역추적하고, 실패를 재료 삼아 지침을 개선하기 위해서다.
2. **외부/내부 저장소 분리** — 보안 등급이 다르고, 사고 시 영향 범위를 끊기 위해.
3. **자동화는 생성까지, 발행 결정은 사람** — 사실 오류 0건 원칙의 최종 방어선.
4. **원문을 재배포하지 않는다** — 저장은 내부 분석용, 발행물은 자체 문장 + 출처 표기.

## 4. 단계 ① 수집 — 글이 시스템에 들어오는 과정

매일 06:00, GitHub Actions(저장소의 코드를 정해진 시각에 클라우드에서 자동 실행하는 기능)가 수집을 시작한다 — 두 사람의 PC가 꺼져 있어도 돈다. 소스 1곳당 흐름:

```
RSS 주소 접속 → 새 글 목록 수신
  → [중복 검사 1] 이미 저장된 URL인가? → 예: 건너뜀
  → 글 본문 페이지 접속 → 본문만 추출 (광고·메뉴 제거)
  → [중복 검사 2] 본문 내용의 지문(해시)이 기존과 같은가? → 예: 건너뜀
     (같은 글이 다른 주소로 재발행되는 경우를 잡는다)
  → 본문이 기준 길이 미만이면 "요약만 확보" 표시 → claim 추출 대상에서 제외
     (Phase 0 교훈: 예고문 몇 줄에서 뽑은 claim은 신뢰할 수 없다)
  → 원문 전문과 문서 정보를 테이블 1(documents)에 저장
```

### 4.1 소스 카탈로그와 신뢰 등급 (티어)

출처마다 신뢰도가 다르므로 등급을 붙여 저장하고, 글을 쓸 때 역할을 다르게 준다. 수집은 프로젝트의 첫 관문이므로, 소스 카탈로그는 즉흥 등록이 아니라 **확정 프로세스**를 거친다 (Phase 1 트랙 α): ① 커버리지 기준 정의(주제 축×티어 매트릭스, 각 주제 축에 T1~T3 최소 1개, 전체 15~25개 상한) → ② 후보 풀 구성(리스트업·벤치마크 역추적·조사 위임) → ③ **실측 검증 — PC와 GitHub Actions 양쪽에서 접속 확인, 통과 소스만 등재** → ④ 확정 회의(빈칸 배치, 소스별 역할 한 줄) → ⑤ 변경 거버넌스 합의. **확정본은 별도 문서가 아니라 `config/sources.yaml` 자체**이며, 아래 표는 그 요약이다(현재는 Phase 0 실측 스냅샷 — 트랙 α 완료 시 v1.0으로 갱신).

| 등급 | 성격 | 대표 소스 예시 | 글에서의 역할 | 현재 상태 (Phase 0 실측) |
|---|---|---|---|---|
| **T1** | 실증 연구·대규모 데이터 | arXiv(cs.CY 컴퓨터와 사회, cs.HC 인간-컴퓨터 상호작용), SSRN, NBER, Stanford HAI AI Index, 학술지(AMJ, Journal of Applied Psychology 등) | 수치 근거 — 가장 믿을 만함 | arXiv 피드 2개 가동 ✅ (문서 58건) |

### 4.2 수집 방법 — 우선순위와 규칙

같은 소스라도 수집 경로가 여럿일 수 있다. 안정성 순으로 다음 우선순위를 따른다.

1. **공식 API** (프로그램용 공식 창구 — arXiv 등이 제공): 가장 안정적. 제공되면 최우선.
2. **RSS**: 대부분 매체의 기본 경로. 소스 추가 시 반드시 `make validate`(모든 피드 접속을 일괄 점검하는 명령)로 검증하고, 실패 사유는 소스 목록 파일(config/sources.yaml)의 note에 기록된다.
3. **뉴스레터 인박스**: 전용 메일 계정으로 뉴스레터를 구독하고 메일함을 자동으로 읽는 경로. **RSS를 안 주는 고품질 소스(컨설팅사)와 유료 매체의 전문(HBR)을 합법적으로 확보하는 핵심 경로**이며, Phase 0에서 확인된 T2 공백과 T4 공백의 복구가 전부 여기에 달려 있다 — Phase 1 최우선 구축 항목. **한계**: 구독 시작 이후 발행분만 수집된다(과거 아카이브는 못 잡음) — 과거분은 아래 별도 전략을 따른다.

**과거 발행분(백필) 전략** — 아카이브 전체 확보는 시도하지 않는다(라이선스·노력 대비 효용 열위). 세 경로로 선별 확보한다:
- **시대를 넘는 통찰 → 이론 카드로**: 오래돼도 유효한 핵심 내용은 이미 TC 경로(이론 카드 큐레이션)가 담당한다. 과거 아카이브 가치의 가장 큰 몫은 이 구조로 이미 흡수된다.
- **수요 기반 백필**: 증거 수집 단계가 "증거 부족"으로 멈춘 토픽이 생기면, 그 주제의 과거 대표 아티클 3~5편을 담당자가 선별해 등록한다. 시스템이 멈춘 지점이 곧 필요한 과거 글의 목록이다.
- **원출처 추적**: 유료 아티클 상당수는 저자의 학술 연구가 원본이다. 원논문 공개본(SSRN 등)을 찾아 T1로 등록하면 페이월 없이 더 강한 근거를 얻는다.
- **대량 확보가 정말 필요하면 — 크롤러가 아니라 계약으로**: 구독 계정 로그인 크롤링은 약관 위반이므로 금지. 정당한 경로는 ① 기관용 데이터베이스(EBSCO 등 — HBR 아카이브 포함, **사내에 기존 기관 구독이 있는지 먼저 확인**) ② TDM(텍스트·데이터 마이닝) 라이선스 — 전문의 DB 저장·AI 분석을 위한 정식 이용권 ③ 발행사와 기업 구독 협상(과월호 접근·내부 저장 허용을 계약 조건으로). 구독 계약 시 확인 질문 3개: 아카이브 접근 범위 / 내부 저장·TDM 허용 여부 / API·일괄 다운로드 제공 여부.

백필용 등록 수단으로 파일 기반 수기 등록(`/ingest-file` — 구독 계정으로 열람·저장한 전문 파일을 등록)을 Phase 1에 구축한다. **전제 조건**: 유료 구독 약관은 통상 개인 열람용이므로, 전문을 내부 DB에 저장·분석하는 것이 허용 범위인지 **기업/기관 구독 계약 시 확인**해야 한다(16장 확인 사항).

4. **HTML 수집** (웹페이지 직접 수집): robots.txt(사이트가 밝힌 수집 허용 규칙)와 이용약관을 준수하고, 요청 간격 3초 이상, 수집 주체 명시. **유료 잠금(페이월) 우회는 절대 금지.**
5. **수기 등록**: 담당자가 발견한 좋은 글을 `/ingest-url 주소` 한 줄로 같은 흐름에 태운다. 본문을 못 가져오는 페이지(구독 전용 등)면 시스템이 우회하지 않고 "정식 구독으로 열람 후 요지를 입력하라"고 안내한다.

**소스 변경 거버넌스** (확정 후에도 목록은 살아있는 문서다 — 단, 규칙으로 바뀐다):
- **추가**: 두 담당자 합의 + `make validate` 통과(PC·Actions 양쪽) + **1개월 시험 기간**(인용 실적 관찰 후 정식 편입)
- **제거**: 월 1회 소스 성과 리뷰에서 **6개월 무인용 소스는 퇴출 후보** — 자주 인용되는 소스와 유사한 소스로 교체. 이 순환이 장기 품질을 좌우한다
- **장애 대응 3단 사다리**: ① URL·파싱 수정으로 살린다 → ② 뉴스레터 경로로 전환한다 → ③ 수기 등록으로 버티거나 제거한다. 모든 소스를 살리려 애쓰지 않는다
- 실무는 목록 파일 편집 → `make validate`가 전부이며, Claude Code에 "○○ 소스 추가해줘"로 시켜도 된다

### 4.3 저작권 원칙 (협상 불가)

발행물에 원문 문장을 옮기지 않는다. 인용은 출처당 1회·최소 길이. 특정 기사의 목차·전개 구조 모방 금지. 모든 발행물 하단에 출처 목록.

## 5. 단계 ② 정제·분해 — 글이 claim이 되는 과정

수집된 문서는 두 개의 관문을 지나 claim으로 분해된다.

**관문 1. 관련성 판별** (Phase 0 교훈으로 추가): 이 문서가 '일·조직·인재·AI와 일'에 관한 글인지 경량 AI가 예/아니오로 판정한다. Phase 0에서 이 관문이 없어서 부동산 기사에서 claim 7건이 추출돼 claim 테이블을 오염시켰다 — 방치하면 토픽 발굴이 "이번 주 주제: 공시가격"을 제안하는 사태로 이어진다. 무관 판정 문서는 보관은 하되 claim을 뽑지 않는다.

**관문 2. claim 추출**: AI가 추출 지침(프롬프트)에 따라 문서에서 검증 가능한 주장을 2~8개 뽑는다. 지침의 핵심 규칙: 원문 문장을 복사하지 말고 자체 문장으로 다시 쓸 것 / 한 claim에 한 명제만 / 수치는 원문 표기 그대로 / 추출할 주장이 없으면 억지로 만들지 말 것. 각 claim에는 근거 유형(실험·설문·사례·이론·의견 등)과 주장 방향(낙관·신중·조건부·중립)이 태깅된다 — **주장 방향 태그가 특히 중요하다. 나중에 "반대 관점을 의도적으로 찾아오는" 검색이 이 태그로 가능해진다.**

**추출 품질은 어떻게 믿는가**: 표본 문서의 추출 결과를 사람이 원문과 대조하는 스팟체크로 관리한다(목표 정확도 90%). Phase 0 실측: 첫 측정 88.9% → 실패 유형 분석(수치 표기 오류, 근거 유형 분류 오류) → 추출 지침 v2로 보강 → 같은 문서 재추출로 개선 확인. **추출 지침은 파일로 버전 관리되므로 "언제 뭘 바꿔서 좋아졌는지"가 이력으로 남는다.**

## 6. 재료 보강 — 이론 카드 (TC)

확립된 조직 이론은 뉴스처럼 새로 발행되지 않으므로 수집이 아니라 **큐레이션** 대상이다. 이론 1개 = 카드 1장(파일)이며, 카드의 "핵심 명제"와 "경계 조건" 항목이 한 줄씩 claim으로 변환되어 테이블 2에 들어간다 — **일반 문서의 claim과 같은 테이블에 들어가므로, 60년 된 이론과 지난주 HBR 기사가 자연스럽게 교차 검색된다.** 이것이 이론을 별도 보관소가 아니라 같은 데이터베이스에 넣는 이유다.

카드 구성: ① 핵심 명제 ② **경계 조건(이 이론이 언제 성립하지 않는가)** ③ AI 시대 연결점 ④ 원전 서지. 경계 조건이 특히 가치 있다 — Phase 0 아티클의 논지가 심리적 안전감 이론의 경계 조건("책무성 없는 안전감은 안주가 된다")에서 나왔다.

**구축 절차와 품질 게이트**: `/add-theory 이론명` → AI가 초안 작성(status: draft) → **사람이 원전과 대조 검수 → reviewed로 변경 + 검수자 기재** → 그때만 시스템이 색인한다. draft 상태 카드는 색인이 거부되고, AI가 스스로 reviewed로 바꾸는 것도 금지되어 있다. 실증 논란이 있는 이론(70:20:10 등)은 비판을 카드에 함께 기재한다. 목표 30장, Phase 0에서 5장 완료.

## 7. 재료 보강 — 내부 자료 (A등급 전용 운용)

내부 자료는 별도 폴더(internal/)에 파일로 등록한다. 파일 맨 위 6줄(제목·유형·발화자·날짜·보안등급·키워드)만 채우고 `/sync-internal`을 실행하면 색인된다. 신년사가 새로 나오면 파일 하나 추가 + "이전 메시지를 대체함" 표시 — 이 대체 관계 덕분에 **철 지난 메시지를 최신인 양 인용하는 사고가 구조적으로 막힌다.**

**운용 규칙은 하나다**: *이 폴더에 올라간 텍스트는 아티클 생성 시 외부 AI 서버로 전송된다. 전송돼도 되는 내용만 올린다.* 올릴지 말지의 판단은 담당자 몫이며, 판단 기준은 "이 문장이 사보에 실려도 괜찮은가"다. 별도 승인 절차는 없다.

**사내한(B등급) 자료의 가치를 쓰는 방법 — 사람이 등급 변환기가 된다**: B등급 원문 파일은 올리지 않는다. 대신 담당자가 읽고 **공개 가능한 수준의 요지**를 직접 작성해 A등급 문서로 등록한다. 추상화 작성 요령: ① 원문 문장을 옮기지 않는다 ② 미공개 수치·미발표 계획·개인 정보를 뺀다 ③ 방향과 개념만 남긴다 ④ 출처를 "2026 하반기 타운홀 메시지 요지(담당자 추상화)"처럼 명시해 원문과 구별한다. AI는 이 요지를 재료로 쓴다.

**남겨두는 안전벨트 (비용 0)**: 파일의 security 표기와, C등급 파일을 시스템이 열어보지도 않고 거부하는 자동 검사는 유지한다. 2인 교대와 미래의 담당자 교체를 생각하면 "이 폴더는 전부 전송 가능"이라는 암묵적 약속보다 파일마다 한 줄 명시가 남는 편이 실수를 막는다. 실수로 B로 표기된 파일이 등록되면 시스템이 전송 대상에서 자동 제외하므로, 이 표기는 최후의 이중 안전장치 역할도 겸한다.

**내부 자료의 역할 원리**: 인용·나열용이 아니라 해석의 렌즈다. "SKMS는 A라 한다, 맥킨지는 B라 한다"(나열)는 반려 사유(R-05)다. 외부에서 발견된 현상을 SKMS의 개념 틀로 재해석해 SK에서만 성립하는 시사점을 만드는 것이 기준이며, Phase 0 아티클은 VWBE를 '안전감 축'에, SUPEX 반복 달성 구조를 '책무성 축'에 대응시키는 방식으로 이를 통과했다.

## 8. 단계 ③~⑥ 집필 — 실제 사례로 따라가는 아티클 1편의 여정

Phase 0에서 발행된 「"실패해도 괜찮다"만으로는 부족하다」가 시스템을 통과한 과정을 실물 그대로 따라간다. 굵은 표시가 사람이 개입한 지점이다 (총 3회).

**③ 토픽 발굴** — 시스템은 최근 2주의 claim들을 의미가 비슷한 것끼리 자동으로 묶고(군집화), 묶음마다 세 가지 신호 점수를 계산한다: 급증도(전주 대비 관련 claim이 얼마나 늘었나) · **논쟁도(낙관 claim과 신중 claim이 얼마나 팽팽한가 — 높을수록 좋은 주제다. 논쟁이 없는 곳에 인사이트도 없다)** · 미개척도(과거 발행 글과 얼마나 겹치지 않나). 후보 5건이 파일로 제시되고, **담당자가 "심리적 안전감과 AI 실험 문화"를 선택했다** (15분).

**④ 증거 수집** — 시스템이 선택된 토픽으로 claim 테이블을 검색해 19건을 모으고, 최소 조건을 검사했다. 실제 기록:
```
독립 출처: 5곳 (이론 카드·HBR·arXiv·McKinsey·MIT SMR)  → 3곳+ 충족
주장 방향: optimistic 2건 vs cautious 5건               → 반대 관점 충족
T1·T2급:  이론 7건 + arXiv 2건 + McKinsey 1건           → 2건+ 충족
→ 통과. 증거 묶음을 JSON 파일로 확정
```
조건 미달이면 여기서 **시스템이 스스로 멈추고 "증거 부족"을 보고한다.** 억지로 쓴 글이 요약체의 온상이므로, 못 쓰는 주를 인정하는 것이 설계 사상이다.

**⑤-1 앵글 설계** — 같은 증거 19건으로 서로 다른 논지 3개가 제안됐다. A안 "병목은 구성원의 두려움이 아니라 리더의 진단 오류다" / B안 "안전감만으로는 안 된다 — 책무성 없는 실험 장려는 파일럿 안주를 만든다" / C안 "고성과 전문가가 AI 위임을 피하는 진짜 이유". 각 안에는 **반증 조건**("무엇이 사실로 확인되면 이 논지가 틀리는가")이 반드시 붙는다 — 반증 조건을 쓸 수 없는 논지는 주장이 없는 글이므로 이 단계에서 걸러진다. **담당자가 B안을 선택했다.**

**⑤-2 초안 작성** — 고정 구조(3줄 요약 → 관찰된 신호 → 통념과의 충돌 → 교차 해석 → SK 맥락 → 다음 주에 시도할 것(리더용·실무자용) → 남은 쟁점 → 출처 목록)로 작성됐다. 모든 문단 뒤에는 근거 claim의 번호가 주석으로 기록된다 — 이것이 다음 단계 검증의 재료다. 분량 기준 1,800~2,500자(실제 2,375자).

**⑤-3 자동 검증** — 검증기는 초안의 주석에서 실제 사용된 claim 번호를 수집한 뒤:
```
수치 대조:   본문의 모든 숫자를 해당 claim의 원문 수치와 대조 → 전건 일치
사용 기준 재검사: "실제 쓰인" claim 기준으로 출처 수·반대 관점 재확인
             (Phase 0 교훈: 모아둔 증거가 아니라 쓴 증거 기준이어야 한다)
40% 룰:     문단별 파생 출처 분석 → 최대 의존 출처(이론 카드) 30% → 통과
            (한 출처가 40%를 넘으면 그 출처의 요약이므로 반려)
금지어 검사: "주목받고 있다" 류 상투어 0건
자체 채점:   루브릭(9장) 23/24 → 18점 임계 통과
```
탈락하면 초안 단계로 자동 회귀한다(최대 2회, 그래도 안 되면 반려 보관).

**⑥ 승인** — **담당자가 체크리스트로 최종 검토했다**: 특정 직군·세대를 싸잡는 표현 없는가 / 경영층 인용(최태원 회장 신년사 1회)이 원문과 일치하고 맥락 왜곡이 없으며 최신 메시지인가 / 검증 리포트 이상 없는가. 사람 채점 22/24로 승인. **이 승인만은 어떤 자동화 단계에서도 사람에게 남는다** — 사실 오류 0건 원칙의 최종 방어선이기 때문이다.

**운영 단계의 간소화**: 사람 개입 3회 중 앵글 선택(⑤-1)은 추후 "시스템 추천 + 사람은 거부권"으로 줄인다. 전환 조건: 초기 운영에서 사람의 선택과 시스템 추천 1위가 70% 이상 일치할 것.

## 10. 전달 방식

**웹 피드(본편) + 카드뉴스 티저(배달) 병행**이 잠정안. 독자가 전 구성원이므로 3~5장 카드 티저를 메신저로 푸시하고 마지막 장에서 웹 본편으로 연결한다. 본편을 카드뉴스로 만들지 않는 이유: 8~10장으로 압축하는 순간 교차 해석이 도로 요약으로 눌린다. 웹에는 주제·기간 아카이브 검색 필수. 웹 구축은 Phase 3이며, 그 전에는 파일럿 독자 20~30명 메일 발송으로 품질을 검증한다 — **품질 검증 전 전 구성원 발행이 최대 위험이다. 첫인상은 회복이 어렵다.**

## 11. 운영 — 사람이 하는 일의 전부

주간 리듬(운영 단계, 주당 90분): 월요일 토픽 선택 15분 → 주중 자동 진행 0분 → 발행 전날 편집·승인 60분 → 예외 대응 15분.

**협업 구조 (2인 체제) — 확정: Supabase 공유 DB + GitHub Actions 스케줄** (2026-08-26, 외부 SaaS 정책·사내망 접속 확인 완료): 데이터(DB·수집 원문)는 **외부 관리형 PostgreSQL(Supabase) 한 곳**에 두고, 수집·추출은 **GitHub Actions가 매일 06:00 클라우드에서 자동 실행**한다. 두 PC는 순수한 작업 단말이 되어 켜짐 여부와 무관하게 아무 PC에서나 `/draft`·`/publish`·스팟체크를 수행한다 — "항상 켜진 머신이 없다"는 제약이 해소되어 핸드오프 체제는 폐기한다(비상용 코드만 유지). 이중 실행은 DB의 일일 수집 잠금으로 방지. 전환 절차는 실행 문서(`docs/phase1-plan.md`) 0단계에 통합되어 있다. 접속 정보(DATABASE_URL)와 API 키는 **어떤 파일에도 쓰지 않고** GitHub Secrets와 각 PC 환경변수로만 관리한다. 저장 데이터의 민감도는 A등급 전용 정책 덕에 낮다(전부 "외부 전송 가능" 기준 통과 자료). Supabase 대시보드로 테이블을 눈으로 확인할 수 있어 비개발 운영에 유리하며, 유료 등급 사용을 권장(무료 등급의 미사용 일시정지 회피). 코드·절차서·산출물은 private Git 저장소로 공유(데이터는 git 제외 원칙 유지).

**2인 교대 규칙**: ① 승인은 감이 아니라 체크리스트로 ② 월 1회 같은 초안을 각자 채점해 비교, 4점 이상 차이 나면 기준 문서 수정 ③ 인수인계는 구두가 아니라 `/status` — 파일 상태가 곧 인수인계 문서 ④ 동시 부재 주는 결호 대신 과거 고성과 글 재발행.

**Claude Code 지시 요령**: 슬래시 커맨드는 프로그램 버튼이 아니라 `.claude/commands/`에 한국어로 써둔 **작업 절차서**다 — 실행 중 대화로 조정할 수 있고, 절차서 파일을 직접 고칠 수도 있다. 주간 루틴의 핵심은 `/draft`와 `/publish` 둘이고, 커맨드에 없는 일은 그냥 한국어로 시키면 된다(자주 반복되면 "이걸 커맨드로 만들어줘"). 새 기능은 "만들어줘 + 테스트 통과 확인해줘"로 지시하고, "비개발자도 이해할 수 있게 설명해줘"는 언제나 유효한 지시다.

| 커맨드 | 하는 일 | 언제 쓰나 | 사람의 역할 |
|---|---|---|---|
| `/collect` | 전 피드 접속 점검 + 수집 실행 + 신규/중복/실패 통계 보고 | 평소 자동(매일 새벽). 소스 추가 후·즉시 수집 시 | 실패 소스의 수정·전환 결정 |

| `/add-theory 이론명` | 이론 카드 초안 작성 후 검수 대기(draft) 상태로 검수 요청 | 이론 카드 확충 시 | **원전 대조 검수 + 완료 표시** — 이것 없이는 색인 안 됨 |
